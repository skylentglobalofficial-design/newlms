# Writing a specification someone can build

**Objective:** Write a thin spec: user, trigger, happy path, one edge case, acceptance check, and an out-of-scope line.

**Why this matters:** “Shared inbox” is a slide. Ambiguity becomes whatever engineering invents on Thursday.

**Prerequisite:** Assignment l12.

**Estimated time:** 50 minutes.

**Case:** [harbor-desk-case.md](/content/product-management/harbor-desk-case.md)

## Explain

A spec in this course is one screen, not a 20-page PRD. Required parts:

1. **User** — who acts
2. **Trigger** — what starts the flow
3. **Happy path** — steps to “owned”
4. **Edge case** — one realistic break (duplicate, mute, walkie-only)
5. **Acceptance check** — how Karthik knows it is done
6. **Out of scope** — what this spec must not grow into

If your spec needs @mentions to function, you have rebuilt Gmail. If it needs a model, you have left the course.

Match the spec to **the bet you chose**. If you chose process-only, the spec is the rota and the Monday log fields — still a spec, still testable.

## Worked example

Assume bet = weekend exception queue (not Gmail).

- **User:** Meena (cashier) or Priya (store lead)
- **Trigger:** Customer delivery failed, or inbound truck is late
- **Happy path:** Open list → new exception (store, type, time, one-line note) → status `open` → HQ or on-call sets `owned` with a name
- **Edge:** HD-07 style duplicate of a Friday thread — allow a “duplicate of” link, do not auto-merge with ML
- **Acceptance:** A reviewer can create an exception and see owner + status without email
- **Out of scope:** file upload, @mentions, warehouse stock, revenue dashboard, mobile offline

Bad spec line: “The system should be intuitive and scalable.” Karthik cannot implement “scalable” in six weeks as a feature.

## Practice

Write the six parts for *your* bet from l12. If you have not written l12 yet, use the exception-queue bet.

Then write one sentence Karthik could screenshot into a commit message.

## Expected result

An engineer who has not attended a meeting could implement the happy path. Out of scope includes at least one Gmail feature.

## Common mistakes

- Spec that ignores the constraint you just chose.
- Acceptance = “users are delighted.”
- Edge case = “server is down” with no Harbor-specific behaviour.

## Knowledge check

**Q.** Should the spec include Northwind `net_revenue`?

**A.** No. Wrong product. If you need a number, use exception counts from the Harbor log.
