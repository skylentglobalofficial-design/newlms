# Problem statements that can be tested

**Objective:** Write a problem statement with user, context, pain, and a way to know it was less true next month.

**Why this matters:** “Stores need better communication” cannot fail. A statement that can fail is usable.

**Prerequisite:** Assignment l6.

**Estimated time:** 45 minutes.

**Case:** [harbor-desk-case.md](/content/product-management/harbor-desk-case.md)

## Explain

Template used in this course:

> **When** [situation], **[user]** cannot [job], so [observable pain]. We would know this was less true if [count / check] by [time].

Too broad: “Retail ops is broken.”
Too narrow: “HD-03 must never happen again exactly as walkie-then-forgotten” — that is an incident, not a problem class.
Solution-shaped: “We lack Gmail.”

A testable Harbor Desk problem names **a class of exceptions** (late inbound, delivery failure) and **an owner gap**, not a vendor.

You do not need a statistics course. You need a count you could take from a future weekend log like the July table.

## Worked example

Rejected: “Harbor Retail needs a modern communication stack.”

Accepted (delivery failures):

> When a weekend customer delivery fails, Meena (and cashiers like her) have no written place to put it, so the customer becomes a personal WhatsApp thread (HD-09, HD-03). We would know this was less true if every weekend delivery failure had a written owner before Monday 10:00.

Accepted (late trucks) is a *different* problem. Do not mash them into one sentence unless you are honestly choosing both — which six weeks may not allow.

Rejected rewrite: “Increase NPS.” There is no NPS in the case.

## Practice

Write:

1. One testable statement for late inbound (Priya).
2. One testable statement for delivery failures (Meena).
3. One rejected rewrite of Arun’s Gmail ask, with a one-line reason.

Pick which statement you would carry into prioritisation and say why in one sentence (constraint, not preference).

## Expected result

Each accepted statement could be argued with next month’s exception table. The Gmail rewrite should not keep “Gmail” in the problem line.

## Common mistakes

- Putting the product name in the problem.
- Using “chaos” as the pain.
- Combining SKU missing + trucks + deliveries so nothing can be cut later.

## Knowledge check

**Q.** Why include “Monday 10:00” in the delivery-failure statement?

**A.** It is a check Arun could run without a new dashboard product. He already reconstructs Mondays. The timebox makes the claim falsifiable.
